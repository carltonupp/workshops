# Concurrency

You've seen concurrency models before - TPL, the CLR thread pool, maybe goroutines. Python has three, and which one you're on is decided per call site, not per process. This section is the one that bites people arriving from other ecosystems.

The three models:

- **asyncio** - a single-threaded cooperative event loop. `async def`/`await` syntax maps almost directly onto C#'s, with one big difference: there is no thread behind an awaitable. Coroutines yield to the loop; nothing runs in parallel, it interleaves. Ideal for many concurrent I/O operations.
- **threads** - real OS threads, but the GIL (Global Interpreter Lock) means only one executes Python bytecode at a time. They shine when work happens outside the interpreter: syscalls, blocking I/O in libraries without async support, C extensions that release the GIL.
- **processes** - separate interpreters, separate GILs; true parallelism for CPU-bound work at the cost of serialising data across process boundaries (`ProcessPoolExecutor`).

On the GIL itself: it's no longer quite forever. Free-threaded builds ship alongside the standard interpreter from 3.13+ (`uv python install 3.14t`), but treat them as early-days - verify your dependency stack supports them before betting anything on it.

FastAPI's dispatch rule ties this together:

- a `def` endpoint runs on anyio's thread pool (capped around 40 threads by default) - perfectly fine for ordinary CRUD
- an `async def` endpoint runs on the event loop - and one blocking call stalls **every** request

Prove the stall to yourself. Add both of these, then hit `/slow` twice concurrently while watching response times:

```python
@app.get("/slow")
async def slow():
    await asyncio.sleep(3)      # correct: the loop stays free


@app.get("/blocked")
async def blocked():
    time.sleep(3)               # wrong: every request queues behind this
```

Now apply it for real. A task tracker that notifies subscribers when work completes needs concurrent outbound calls. Add `uv add httpx` (it moves from dev dependency to runtime dependency) and build the fan-out with `asyncio.gather`:

```python
async def notify(client: httpx.AsyncClient, url: str) -> int:
    response = await client.post(url, json={"event": "task.completed"})
    return response.status_code


async def complete_task(task_id: int, session: Session = Depends(get_session)):
    ...
    async with httpx.AsyncClient(timeout=5) as client:
        results = await asyncio.gather(*(notify(client, url) for url in subscriber_urls))
```

For the CPU-bound counterpart - say, generating a summary report over all tasks - don't put it on the event loop and don't reach for processes yet; hand it to the thread pool:

```python
from anyio import to_thread

report = await to_thread.run_sync(build_report, session_payload)
```

Rules of thumb to leave with: keep CRUD endpoints synchronous until you have a concrete reason not to; go `async` only when the library underneath is genuinely async; offload blocking or CPU-heavy calls so neither the loop nor the pool is starved.
