# The FastAPI mental model

FastAPI has one central trick, and everything follows from it: it reads the type hints on your endpoint signatures and derives routing, request parsing, validation, serialisation and the OpenAPI schema from them. If you know ASP.NET Core's minimal APIs, it's the same idea taken further - the annotation is the contract.

```python
from datetime import date
from enum import Enum
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Task Tracker")


class Priority(str, Enum):
    low = "low"
    medium = "medium"
    high = "high"
    critical = "critical"


class TaskCreate(BaseModel):
    title: str
    description: str | None = None
    priority: Priority = Priority.medium
    due_date: date | None = None


@app.post("/tasks", status_code=201)
def create_task(task: TaskCreate) -> TaskCreate:
    ...
```

How parameters are interpreted: scalar types become query parameters, Pydantic models become the JSON body, anything matching a path segment becomes a path parameter. Optional query params for filtering are just optional arguments: `def list_tasks(status: Status | None = None)`.

Things worth knowing upfront rather than discovering in production:

- Invalid requests are rejected with a structured 422 automatically. Don't hand-roll input validation - Pydantic already did it.
- Return annotations (or `response_model`) filter output. Use narrower output models than your tables so internal fields never leak.
- `def` endpoints run on a threadpool; `async def` runs on the event loop. Only mark handlers async when doing genuinely async IO - blocking calls inside `async def` stall every request. The concurrency section unpacks this properly.
- `Depends` is the built-in DI container; dependencies can be yield-based for setup/teardown and are cached per-request by default.
- Startup/shutdown goes in a lifespan context manager, not module-level side effects.
