# Structure and shipping

A single file works until it doesn't. The layout used by most real FastAPI codebases maps closely onto controller-per-area thinking from ASP.NET Core:

```
app/
  __init__.py
  main.py        # app factory, router registration, lifespan
  database.py    # engine, get_session
  models.py      # Task, Project and their Pydantic variants
  routers/
    tasks.py
    projects.py
```

Endpoints move into an `APIRouter` - effectively a controller group with its own prefix and OpenAPI tag:

```python
from fastapi import APIRouter

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.get("")
def list_tasks(...):
    ...
```

```python
app.include_router(tasks.router)
app.include_router(projects.router)
```

With that structure in place, add the `Project` entity using the workflow you've now practised twice: model family, CRUD router, then relate tasks to their project so the brief's filter-by-project falls out of the existing query pattern. Keep the tests green throughout - if they go red, that's the safety net working.

One thing worth adding before anyone asks: `pydantic-settings` gives you strongly typed configuration bound from environment variables (your `IOptions` pattern), so `sqlite:///tasks.db` stops being hardcoded and environments stop being code changes.

On shipping:

- `uv run fastapi run` wraps uvicorn with production settings and worker processes
- Once schema changes outlive development, replace `create_all` with Alembic migrations - the EF Migrations analogue
- The natural next requirement is authentication; API key auth over these endpoints is exactly what our sibling workshop `agentic-coding-basics` builds with agentic tooling, if you want to see the same problem solved a different way

Finally, walk the brief requirement by requirement against `/docs`. Anything missing is your backlog; anything ticked is delivered.
